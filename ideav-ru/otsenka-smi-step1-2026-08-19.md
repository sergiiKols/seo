# Оценочная проверка SMI: как программа определяет направления и почему ядро вышло таким

Дата: **19.08.2026**. Проверен репозиторий `github.com/sergiiKols/smi-los`
(202 МБ, 1 453 файла). Проверка оценочная — читал ключевые узлы конвейера,
не весь код.

Первая ссылка (`smi-los1`) вела в другой проект — автопубликатор статей для
`energo-audit.by`, семантики там нет. Здесь — та самая программа.

## 0. Оговорка о версии, без которой выводы можно не так прочитать

В репозитории **один коммит от 26.02.2026**. Ядро `keywords_all.csv`
собиралось позже: скрапер Wordstat интегрирован к июню (паспорт на сервере
датирован 12.06.2026), выгрузка сделана 05.08.2026.

Видно и по коду: в репозитории **нет** ни `SCRAPER_URL`, ни маршрута
`/api/seo/step2/wordstat/upload-results`, на который скрапер шлёт результаты.
То есть рабочая версия ушла вперёд минимум на четыре месяца.

Ещё одно косвенное расхождение: в репозитории кластер именуется
**самой частотной фразой внутри себя** (`database.py:1583`), а в выгрузке
колонка «Подпапка» содержит редакторские названия — «Определения и понятия»,
«Жизненный цикл», «Управление бизнес-процессами». Значит именование
кластеров с февраля переделали.

**Поэтому:** архитектурные выводы ниже переносятся на рабочую версию с
высокой вероятностью, конкретные строки — надо сверить по вашей копии.

## 1. Главное: на step1 нет определения направлений

`Step1InitialData.tsx` (1 179 строк) — это **форма исходных данных**, и
только: URL сайта, страна, выбор провайдера (свой сбор / Topvisor),
поисковик, OAuth-токен Wordstat, гео, ключ Serper, режим SERP-парсера.
Ни анализа сайта, ни определения тематики, ни направлений там нет —
ни строки.

Направления в этой версии рождаются **на шаге 4**, и вот как:

```
ключевые слова проекта
  → BERTopic (semantic_clustering.py)          — кластеры по смыслу фразы
  → имя кластера = самая частотная фраза в нём (database.py:1583)
  → Qwen AI группирует ИМЕНА кластеров          (qwen_clustering_grouper.py)
  → направления верхнего уровня                 (api_server.py:5845)
```

**Сайт в этой цепочке не участвует вообще.** Ни `site_url`, ни тексты
страниц, ни продукт, ни оффер. «Направления сайта» — это на самом деле
направления того списка слов, который уже лежит в базе. Что в список
попало, то и станет тематикой сайта.

Если в вашей версии определение направлений действительно переехало на
step1 — это как раз то место, которое надо смотреть первым, и я его пока
не видел.

## 2. Восемь находок по коду

### 2.1. Одна колонка на две несовместимые частоты — корень расхождений

Bukvarix отдаёт **обе** частоты, широкую и точную
(`api_server.py:4818-4823`). При сохранении они схлопываются в одно поле:

```python
kw.get('exact_frequency', kw.get('broad_frequency', 0))   # api_server.py:4904
```

Отдельно работает Wordstat: `/v1/topRequests` → `totalCount`
(`wordstat_api.py:59, 105`) — это **широкая** частота, оператора кавычек
в запросе нет. Она пишется в **другую** колонку:

```sql
UPDATE keywords SET yandex_frequency = ?   -- wordstat_api.py:200-203
```

В экспорт уходит `yandex_frequency` («Частота Yandex»), то есть **широкое
соответствие**, а точная частота из Bukvarix остаётся в поле `frequency`
и в выгрузку не попадает.

Отсюда ровно то, что мы видели в ядре: «система автоматизации отчетности»
699 при точном замере 156, при том что самой фразы в Wordstat нет.

### 2.2. Ноль означает три разные вещи

При ошибке API фраза получает ноль:

```python
frequencies[phrase] = 0   # wordstat_api.py:104, 109 — и при error, и при неожиданном ответе
```

Плюс ноль стоит у ещё не снятых фраз. Плюс ноль — законный результат для
низкочастотника. Различить их в выгрузке нечем. В ядре таких строк 837.

### 2.3. Числа не обновляются никогда

```sql
WHERE project_id = ? AND (yandex_frequency IS NULL OR yandex_frequency = 0)
-- wordstat_api.py:161
```

Обновляются только фразы **без** частоты. У кого число есть — оно
замораживается навсегда, независимо от возраста. Даты съёма в базе рядом с
числом нет. Так в одном файле оказываются числа разных месяцев.

### 2.4. Дедуп по точному совпадению строки

```sql
SELECT id FROM keywords WHERE project_id = ? AND keyword = ?   -- api_server.py:4889
```

SQLite сравнивает TEXT побайтово. «Учет клиентов» и «учет клиентов» —
две записи. «аналог гугл таблиц» и «гугл таблицы аналог» — две записи.
Нормализации (регистр, порядок слов, лемма) нет нигде. Отсюда 51% дублей
в выгрузке.

### 2.5. Кластеризация не знает ни частоты, ни интента

`BERTopic` на эмбеддингах `paraphrase-multilingual-MiniLM-L12-v2`
(`semantic_clustering.py:47-84`) работает **только с текстом фразы**.
Ни частота, ни коммерческий интент, ни принадлежность странице в модель
не подаются.

Поэтому «информационные системы и технологии егэ» (абитуриент) и
«информационная система для бизнеса» (покупатель) садятся рядом: по
эмбеддингу они близки, по смыслу для бизнеса — противоположны.

### 2.6. Выбросы BERTopic выброшены молча

```sql
WHERE cluster_id = ? AND topic_id != -1   -- api_server.py:5868, 5974
```

`topic_id = -1` — это выбросы BERTopic, всё, что не легло ни в один
кластер. Они не попадают ни в кластеры, ни в направления, ни в UI
(`semantic_clustering.py:154`). Пользователь не видит, сколько потерял.
В выгрузке это те самые **63% строк с пустой «Подпапкой»**.

### 2.7. Направления делает LLM по одним лишь названиям кластеров

`qwen_clustering_grouper.py` отправляет модели **только список имён**:

> Ты — опытный SEO-аналитик… Сгруппируй эти кластеры в направления
> верхнего уровня по смысловой близости.

Модель не получает ни частот, ни интента, ни сайта, ни продукта, ни
списка страниц. При этом правило 7 требует группировать «логично с точки
зрения бизнеса и поисковых интентов» — данных для этого у неё нет.

Результат предсказуем: получается **академическая таксономия предметной
области**. Семь направлений Интеграма — «BPM и автоматизация бизнес-процессов»,
«Процессный подход к управлению», «Информационные системы и цифровая
трансформация» — это оглавление учебника, а не карта спроса. Ни «учёта»,
ни «замены Excel», ни ВПР там нет и быть не могло.

### 2.8. Число направлений задано промптом, а не данными

> 3. Направлений должно быть от 5 до 15 (оптимально 7-12).

Модель обязана выдать столько, сколько велено. У проекта Интеграм ровно
семь — нижняя граница. Если реальная структура спроса требует трёх крупных
и одного мусорного — этого не будет, промпт запрещает.

**Что сделано хорошо:** `validate_qwen_response` проверяет, что ни один
кластер не потерян, не задублирован и не выдуман. Это правильная защита,
и она работает. Проблема не в валидации, а в том, что на вход модели
подаются не те данные.

## 3. Замкнутый круг, который и породил дефекты ядра

Собранное вместе, это выглядит так:

1. Частоты приходят **широким соответствием** → крупнейшими фразами
   становятся агрегаты Вордстата вроде «информационная система и технологии»
   (51 188).
2. **Имя кластера — самая частотная фраза в нём** (`database.py:1549-1583`)
   → кластеры называются агрегатами.
3. **Направления — группировка имён кластеров** → направления собираются
   из агрегатов.
4. Направления становятся затравками для следующего круга сбора → в ядро
   приходит ещё больше окрестностей тех же терминов.

Ядро описывает не спрос, а **окрестность термина в Вордстате** — и с каждым
кругом всё сильнее.

Соответствие с разбором `razbor-oshibok-yadra-2026-08-19.md`:

| Дефект ядра | Узел в коде |
|---|---|
| Завышение широким соответствием | `wordstat_api.py:59-65` — `topRequests` без операторов |
| Точная частота потеряна | `api_server.py:4904` — две частоты в одно поле, в экспорт идёт широкая |
| Агрегаты «ИС и X» — 20% веса | следствие 1 + именование кластеров по максимуму частоты |
| Учебный интент 15% | `semantic_clustering.py` — интент не участвует в кластеризации |
| 51% дублей | `api_server.py:4889` — дедуп по точному совпадению строки |
| 837 нулей | `wordstat_api.py:104, 109` — ошибка API пишется нулём |
| «Подпапка» пуста в 63% | `api_server.py:5868` — выбросы BERTopic отброшены |
| «Частота Google» = 0 везде | источника Google в конвейере нет |
| Нет даты и региона у числа | схема `keywords` их не хранит |
| Направления не про бизнес | `qwen_clustering_grouper.py` — модель видит только имена |

## 5. Что чинить, по цене ошибки

1. **Разделить широкую и точную частоту в схеме** — две колонки, у каждой
   свой источник и своя дата. Пока их одна, любое решение по фразе
   принимается вслепую. Это чинит половину дефектов ядра.
2. **Ноль ≠ ошибка ≠ не измерено** — три разных состояния, три разных
   значения (`NULL`, `0`, признак ошибки).
3. **Нормализация фразы при вставке** — регистр, `ё`, порядок слов, лишние
   пробелы. Одна фраза = одна строка.
4. **Показывать выбросы кластеризации** — сколько слов не легло никуда.
   Сейчас 63% ядра исчезает беззвучно.
5. **Дать модели данные для группировки** — частоту кластера, долю
   коммерческого интента, страницы сайта. И убрать из промпта
   предписанное число направлений: пусть его диктуют данные.
6. **Хранить рядом с числом регион и дату съёма.** Без них число не
   значит ничего.
7. **Добавить фильтр агрегатов Вордстата** — фразы вида «X и Y» с
   аномально высокой широкой частотой и нулевой точной. Их надо помечать
   как маркеры темы, а не как запросы.
