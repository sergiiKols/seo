# Аудит страницы — excel-to-app.html

Дата: **05.08.2026**. `https://ideav.ru/excel-to-app.html`. Одна из семи страниц
продуктового раздела ideav.ru (см. общий свод по всем семи).

**Общий вердикт: главная страница воронки конверсии («Excel → приложение»), и
у неё единственная, но критическая техническая проблема — 62% содержимого
существует только после выполнения JavaScript.** Остальные измерения —
типографика, семантика, доступность — вторичны по сравнению с этим.

---

## 0. Главная находка — расхождение сырого HTML и отрендеренной страницы

Это не гипотеза, а измеренный, дважды перепроверенный факт.

| | Сырой HTML (`curl`) | После рендера в браузере (Playwright) | Разница |
|---|---|---|---|
| Слов видимого текста | **288** | **761** | +473 слова, **+164%** |
| `<h2>` | 4 («Шаг 1/2/3», «Частые вопросы») | **7** | +3 раздела целиком |
| Ссылок `<a href>` | **8** (7 уникальных) | **48** (31 уникальная) | +40 ссылок |

Семь разделов H2 после рендера: «Прекратите подстраивать бизнес под софт»
(сравнительная таблица Интеграм / тяжёлые SaaS / кастомная разработка), «Как
это работает», «Что конкретно вы получите через 45 минут?», «Ваши данные —
ваша собственность», **«Загрузите свои таблицы»** (сама форма загрузки!),
«А что у конкурентов?», «Читайте в блоге». Из них в сыром HTML присутствуют
только «Как это работает» (частично, как отдельные H2 на каждый шаг) и «Частые
вопросы» — **пять из семи содержательных блоков, включая саму форму
конверсии, отсутствуют в исходном ответе сервера.**

Проверено дважды независимо (`document.body.innerText` и ручная разметка
заголовков через `document.querySelectorAll`), числа сходятся.

**Почему это важно и чем отличается от остальных двух уже разобранных
страниц.** Главная страница и страница сравнения с Битрикс24/AmoCRM грузят
**тот же самый JS-бандл** (`/assets/index-2WEJSy7f.js` — идентичное имя файла
на всех трёх страницах), но их сырой HTML уже содержал практически весь
видимый текст (проверено сегментной разбивкой скриншота для главной странице).
Значит сайт использует серверный рендеринг (SSR/SSG) для части страниц, но
**конкретно на `excel-to-app.html` больше половины контента, включая саму
форму лидогенерации, рендерится только на клиенте.** Это не общее свойство
платформы — это состояние именно этой страницы, и стоит проверить остальные
четыре страницы раздела на тот же симптом.

**Что это значит практически.** Google в 2026 году в большинстве случаев
исполняет JavaScript при индексации, но делает это отложенной второй волной
и не гарантированно для каждой страницы и каждого визита краулера. Яндекс
исторически рендерит JS менее надёжно. **Простая, недорогая проверка,
которую стоит сделать заказчику самому:** Google Search Console → «Проверка
URL» → «Просмотреть просканированную страницу» — там видно, что именно
Googlebot реально получил и обработал для этого адреса. Без этой проверки
нельзя знать наверняка, индексируется ли форма и три ключевых раздела
контента.

## 1. Мета и структурированные данные — не зависят от рендера, всё на месте

JSON-LD — статический `<script>`-тег, серверный рендеринг тут ни при чём,
поэтому эта часть надёжна независимо от находки выше.

| Элемент | Значение |
|---|---|
| title | «Загрузите Excel — получите приложение за ~45 минут \| Интеграм» |
| meta description | «Пришлите Excel-файлы и тематику — вернём ссылку на готовое веб-приложение на платформе Интеграм. Замена Excel на приложение без кода примерно за 45 минут.» |
| canonical | самоссылающийся, корректно |
| og:type | `website` |

**JSON-LD:** `WebPage` + `Service` + `FAQPage` (3 вопроса) + `BreadcrumbList`
(«Интеграм → Из Excel — приложение»). `Service`, а не `Article` — верно для
жанра «продуктовая функция», поэтому отсутствие `datePublished` здесь не
находка (это поле для Article/статей, не для Service).

**Находка:** `og:image` — снова общая картинка `/og/knowledge-base.png`, та же,
что у главной страницы и у страницы сравнения. Три из трёх проверенных на
сегодня страниц переиспользуют одну и ту же OG-картинку — системный паттерн,
не случайность одной страницы.

## 2. Заголовки — структура в порядке, если считать после рендера

Один H1, семь H2 без пропуска уровней, девять H3 (три шага + шесть карточек
«что вы получите» и «ваши данные»), плюс три H3 у вопросов FAQ. Иерархия
логичная. **Оговорка** — вся эта иерархия оценивается по отрендеренному DOM;
по сырому HTML заголовков в 2,25 раза меньше (см. п. 0).

---

## 3. Картинки

Один `<img>` на странице — счётчик Яндекс.Метрики, не контентное изображение.
Контентных изображений — ноль, как и на главной странице и странице сравнения.
Для страницы, которая продаёт «превращаем таблицу в приложение за 45 минут»,
отсутствие хотя бы одного скриншота результата (готового приложения) — заметный
пробел в доказательности, а не только техническая деталь.

Перелинковка с этой страницы — сильная сторона (при условии, что она реально
видна поисковику — см. п. 0).

## 5. Браузерный технический аудит

`screen-audit`, семь разрешений: **2 «стоп» · 16 «чинить» · 3 «знать»**.
Проверено визуально по `mobile-320.png` и `desktop-1440.png`.

### Подтверждено визуально как реальные

- **Фокус не виден у элементов формы** (`textarea.w-full`, `input.w-full`,
  `button.w-full`) — «стоп». Это поля самой формы загрузки Excel: пользователь
  с клавиатурой не видит, на каком поле находится фокус. Для страницы, чья
  единственная цель — заполнение формы, это находка первого приоритета.
- **Кнопка без доступного имени** (`button.text-slate-500`) — тот же класс,
  что на главной и на странице сравнения. Общий элемент (вероятно, переключатель
  темы в шапке), чинить один раз на уровне компонента.
- **28 целей касания меньше 44×44px**, мелкий текст 14px, интерлиньяж ниже
  1.35 на телефоне — тот же класс находок, что на других страницах раздела.

### Признаны ложными после проверки по снимку

- **«Контраст 1:1»** у кнопок «Загрузить файлы», «Отправить и получить
  приложение», «Принять» (cookie) — на `desktop-1440.png` все три кнопки
  отчётливо синие с белым текстом, прекрасно читаются. Тот же механизм ложного
  срабатывания, что на странице сравнения: наш измеритель контраста не
  справляется с закрашенными/градиентными фонами.
- **«Переполнение `header.fixed` на 311px»** — тот же паттерн, что на странице
  сравнения: `position:fixed`-элемент (шапка либо cookie-баннер) «впечатывается»
  в случайное место полностраничного скриншота при склейке. Числа (311, 63,
  95 px) идентичны найденным на `sravnenie-s-bitrix-amocrm.html` — это
  подтверждает, что дефект в общем компоненте шапки, а не в контенте страницы,
  и что это артефакт метода съёмки, а не реальная поломка вёрстки.
- **`input.sr-only` переполнение 216px** — `sr-only` означает «видно только
  скринридеру», элемент намеренно спрятан визуально; переполнение
  невизуального элемента не имеет пользовательских последствий, не чинить.

## 6. Типографика (`ru-text`) — по полному отрендеренному тексту

Кавычки, тире, десятичный разделитель — чисто. **55 случаев отсутствия
неразрывного пробела** после однобуквенных предлогов/союзов на 761 слове —
та же плотность (примерно 1 на 14 слов), что и на других проверенных
страницах сайта: похоже на системную особенность вёрстки, а не единичный
недосмотр.

## 7. Семантическое ядро

**Точных вхождений на полном отрендеренном тексте — три**, и два из них с
нулевой частотой в загруженном ядре. Единственное содержательное совпадение:

| Частота | Фраза | Где |

| 518 | вместо excel | текст (в блоке «А что у конкурентов?») |

**Это самая тонкая семантическая находка всего проекта.** Страница, чья
ЕДИНСТВЕННАЯ функция — «превратить Excel в приложение», не содержит ни одной
из тяжёлых по объёму фраз из кластера, прямо посвящённого автоматизации Excel
(полный список — `semantic-core-on-excel-to-app.csv`):

| 283 | аналог excel | Преодоление технических лимитов |
| 283 | аналоги excel | Преодоление технических лимитов |

страницы и целиком не покрыт буквальными фразами, хотя семантически страница
именно об этом.

## 8. Рекомендации

**Критично, требует решения владельца продукта, не только текста:**
1. **Проверить в Google Search Console → «Проверка URL», что Googlebot
   реально видит после рендера.** Если форма и три раздела не индексируются —
   это не вопрос текста, а вопрос архитектуры рендеринга страницы. Возможные
   решения: перевести эти секции на серверный рендеринг (как уже сделано для
   аналогичного контента на главной странице — значит платформа это умеет),
   либо добавить `<noscript>`-дублирование ключевого текста, либо явно
   принять риск.

**Текст (после решения по п. 1, дёшево, высокий эффект):**
2. Добавить в раздел «Прекратите подстраивать бизнес под софт» или в первый
   абзац буквальную фразу «аналог Excel» или «автоматизация Excel» — сейчас
   слово Excel есть, но эти конкретные, весомые по объёму формулировки — нет.
3. В FAQ добавить вопрос «Чем это отличается от макросов/автоматизации в
   самом Excel?» — закрывает «excel автоматизация процессов» и режет
   возражение читателя одновременно.

**Технические параметры:**
4. Своя `og:image` для страницы вместо переиспользуемой картинки базы знаний
   (системный паттерн на трёх страницах подряд — стоит решить один раз для
   всего сайта).
5. Починить видимый фокус на полях формы (`textarea`, `input`, `button`) —
   первый приоритет по доступности именно на этой странице.
6. Доступное имя для `button.text-slate-500` — общий компонент, чинить один раз.
7. Прямая ссылка на `/knowledge-base.html` вместо `/knowledge-base` без
   расширения.

**Перелинковка:** уже сильная сторона страницы (см. п. 4) — донастройка не
требуется, если подтвердится, что она видна поисковику.

**Обсудить, не чинить:**
8. Ноль контентных изображений на конверсионной странице — решение о
   содержании, но для страницы, продающей наглядный результат («получаете
   приложение»), стоит обсудить хотя бы один скриншот готового приложения.

## 9. Стратегия продвижения по семантическому ядру

Ближайшее направление в ядре — **«Автоматизация рутинных операций и
отчётов»** (247 строк всего в ядре, из них подпапка «Автоматизация Excel» —
14 строк с суммарной частотой около 800) и смежный кластер «Преодоление
технических лимитов и масштабирование» (1508 строк, где живут «аналог excel»,
«лимиты excel», «формулы excel»). Ни один из этих кластеров сейчас не является
основным источником трафика сайта (для сравнения — кластер «информационная
система» на порядок больше), но именно они **точнее всего описывают
конкретную функцию этой страницы** — их и стоит закрывать здесь, а не
перетягивать сюда трафик по неродственным темам.

Приоритетный список фраз для встраивания (частота × прямая релевантность
функции страницы):
1. «аналог excel» / «аналоги excel» (283) — прямое позиционирование.
2. «автоматизация excel таблиц» (160) — заголовок или подзаголовок раздела «Как это работает».
3. «преимущества электронных таблиц» (136) — материал для вводного абзаца, объясняющего проблему.
4. «аналог гугл таблиц» (125) — страница уже упоминает «Google Sheets-экспорт» в форме, но не эту формулировку текстом.
5. «excel автоматизация процессов» (103) — формулировка для FAQ.
